# KTL-33 key runbook

**Losing the key file loses every candidate's data, backups included.** There is no recovery
without it. Read this before generating, moving or rotating keys.

## The key file

A JSON file with two independent purposes, each holding one or more 256-bit random keys and the
identifier of the active one:

```json
{
  "encryption": { "active": "e1", "keys": { "e1": "<base64>" } },
  "blindIndex": { "active": "b1", "keys": { "b1": "<base64>" } }
}
```

Keys are generated by the tool from a cryptographic random source. They are never chosen by a
person and never derived from a password.

**Where it lives.** On the Docker host, outside the repository and outside `backups/`. Compose
mounts it into the `api` container only, as the secret `ktl_field_keys`
(`/run/secrets/ktl_field_keys`), from `KTL_FIELD_KEYS_FILE` (default `./secrets/field-keys.json`,
ignored by git). The `migrator` never receives it. Restrict the host file to the account that runs
Docker.

**Never** put it in PostgreSQL, `.env`, `backups/`, a ticket, chat or git.

## Running the tool

`ktl-migrate` is operator-only. PostgreSQL is not exposed to the host, so run the published tool in
a throwaway .NET runtime container on the stack's internal network:

```powershell
dotnet publish backend/Tools/DataMigration/DataMigration.csproj -c Release -o D:\ktl-tools\ktl-migrate
$keys = "D:\ktl-secrets"          # the folder holding field-keys.json
docker run --rm --network kepler-talento_backend `
  -v "D:\ktl-tools\ktl-migrate:/tool:ro" -v "${keys}:/keys" `
  mcr.microsoft.com/dotnet/aspnet:10.0.2-alpine3.23 `
  dotnet /tool/ktl-migrate.dll encryption <command> --keys /keys/field-keys.json [--connection "<runtime connection>"]
```

`generate-keys`, `add-key` and `retire-key` need no database and can run directly on the host with
`dotnet ktl-migrate.dll encryption ...`. A `libgssapi_krb5.so.2` warning from the runtime image is
harmless.

| Command                                        | Does                                                                                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `generate-keys --out <file>`                   | New key file. Refuses to overwrite.                                                                                                  |
| `add-key encryption\|blindIndex --keys <file>` | Adds a key for that purpose and makes it active. Old keys stay readable.                                                             |
| `retire-key <id> --keys <file>`                | Removes a non-active key.                                                                                                            |
| `backfill --connection <c> --keys <file>`      | Encrypts plaintext, re-encrypts values under non-active keys, recomputes blind indexes. Idempotent, resumable. Run as `ktl_runtime`. |
| `report --connection <c> --keys <file>`        | Counts per table, column and key; decrypts everything. Exit 0 only when clean.                                                       |

## Escrow

Immediately after `generate-keys`, and after every `add-key`:

1. Store a copy of the file in the corporate password manager or vault, **or** print it and seal it
   in a safe.
2. At least two named people must be able to reach the copy. Record who, and where, in the
   operations register (not in this repository).
3. Prove the copy works: the restore drill below.

## Restore drill

Run after the first rollout and after every rotation.

1. Restore the latest recovery set into a non-production stack
   (`scripts/operations/restore.ps1 -RecoveryId <id> -ConfirmNonProduction`).
2. Mount the **escrowed** copy as that stack's key file, not the production file.
3. Run `encryption report` against it. It must end with "every value is encrypted and readable".
4. Start the API and open one candidate.

## Rotating the encryption key

1. `encryption add-key encryption --keys <file>` — adds `e2` and makes it active. Escrow the file.
2. Restart the API. New writes use `e2`; values under `e1` still read.
3. `encryption backfill` — re-encrypts every value under `e1`.
4. `encryption report` — no column may list `e1=` any more.
5. `encryption retire-key e1 --keys <file>`, restart the API, escrow the file again.
6. Retire recovery sets taken before step 3 on the normal retention schedule; they need the old
   key, so keep an escrowed copy of the pre-rotation file until the last of them is gone.

## Rotating the blind-index key

Same steps with `add-key blindIndex` and `retire-key b1`. Between steps 2 and 4, import duplicate
detection looks up both keys, so no downtime is needed.
