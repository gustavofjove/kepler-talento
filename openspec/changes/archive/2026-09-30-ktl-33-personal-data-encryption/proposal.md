## Why

Candidate personal data is stored in plaintext PostgreSQL columns, so anyone who obtains a copy of
the database — a `pg_dump` run by any account with read access, a copied data volume, a VM snapshot
or a recovery set from `backups/` — can read every candidate's identity, contact details, notes and
career history with standard tools. The business requirement (KTL-33) is that such a copy must be
unreadable without keys that are held separately from the database and its backups.

## What Changes

- **Field-level encryption in the API.** Every human-entered free-text column on candidate tables
  is stored as AES-256-GCM ciphertext, encrypted on write and decrypted on read by the API through
  EF Core value converters. Entities, handlers and the HTTP contract keep plain strings.
- **Keys outside the database.** Two random 256-bit keys (encryption, blind index), generated by a
  tool and delivered to the API as a mounted key file. The API refuses to start without valid keys
  in every environment; there is no plaintext mode.
- **E-mail blind index.** A new `EmailHash` column (HMAC-SHA256 of the normalized e-mail) replaces
  the SQL comparison on the e-mail column for import deduplication.
- **Text search and last-name sort run in the API.** When a search carries free text or sorts by
  last name, SQL applies every other filter and the API decrypts, matches, sorts, counts and pages.
  Search results, totals and ordering are unchanged for users; a documented candidate-count ceiling
  and latency budget are added.
- **Search text stored in presets and position requirements is encrypted** inside their JSON
  documents, because a saved search term can be a candidate's name.
- **Schema migration and backfill.** Encrypted columns are encrypted in place: they widen to
  `text` envelopes and gain checks that reject unencrypted new writes; the name indexes and the
  `CK_CND_Candidates_Name` length check (which cannot inspect ciphertext) are dropped; `EmailHash`
  and its index are added with runtime grants. A `ktl-migrate` command encrypts existing rows
  idempotently and reports reconciliation, and the API refuses to start until it has; rotation
  reuses the same command.
- **Build-time query guard.** A test fails when an encrypted property appears in a query filter,
  ordering or grouping, because such a query does not fail at runtime — it silently returns nothing.
- **BREAKING (operations only):** the stack no longer starts without the key file, restores need
  the escrowed keys, and direct SQL, reporting or DBA queries see ciphertext instead of candidate
  data. The HTTP API and the SPA do not change.

## Capabilities

### New Capabilities

- `personal-data-encryption`: which candidate data is encrypted at rest, key format, delivery,
  custody and rotation, fail-closed startup, tamper detection, the e-mail blind index, the query
  guard, backfill and the "no plaintext in the database" guarantee.

### Modified Capabilities

- `candidate-search`: adds the requirement that free-text matching and name ordering keep their
  exact current semantics over encrypted fields, with a documented candidate-count ceiling and
  latency budget.
- `candidate-persistence`: the candidate record field set is persisted encrypted, and required
  identity is enforced by application validation because the database can no longer inspect the
  value's length.

## Impact

- **Actors.** Recruiters and administrators see no change. Operators must provision, escrow and
  rotate keys. Anyone querying PostgreSQL directly loses readable candidate data by design.
- **Key entities.** `Candidate` (identity, contact, location, availability, source, notes),
  `CandidateNote`, `CandidateExperience`, `CandidateEducation`, `CandidateLanguage` and relation
  notes, `CandidateDocument.OriginalFileName`, saved search presets and position requirements (text
  member only). Identifiers, catalog references, status, flags, timestamps, source keys, storage
  keys, hashes and scan codes stay in clear.
- **Code.** New `IFieldProtector` and blind-index abstractions (`Application/Abstractions`), AES-GCM
  implementation and key loading (`Infrastructure`), value converters in the EF configurations,
  `CandidateSearchQuery` (text and name-sort path), `ImportRunSupport` (deduplication),
  filter-document persistence for presets and positions, `Tools/DataMigration` (backfill and
  rotation commands), `Program.cs` startup validation, Compose secret wiring.
- **Database.** One EF Core migration, then an operator backfill and `VACUUM FULL` of the affected
  tables in a maintenance window. `ktl_runtime` grants cover the new column only.
- **Dependencies.** None added: `System.Security.Cryptography.AesGcm` and `HMACSHA256` ship with
  .NET.
- **Performance.** Detail, create, update and default-ordered search are effectively unchanged.
  Text search and last-name sort read every row passing the other filters; the design sets the
  budget (p95 ≤ 300 ms at 12 000 candidates).
- **Personal data and least privilege (principles 1 and 3).** This change exists to strengthen
  principle 1: the database, its dumps and its backups stop containing readable candidate data.
  Keys never reach PostgreSQL, logs, responses, `.env`, `backups/` or git; decryption happens only
  inside the API process for the duration of a request. Principle 3 is preserved: permission
  checks, fail-closed endpoints, runtime/migrator role separation and private document storage are
  unchanged, `ktl_migrator` never holds the keys, and the API itself fails closed when keys are
  missing or invalid. No RLS policy, storage access rule or role definition changes.
- **Assumptions.** About 3 000 candidates today and fewer than 12 000 within the planning horizon;
  no corporate key vault is available, so a key file is used; the PostgreSQL image stays
  `postgres:17.6-alpine`.
- **Edge cases.** A value encrypted under a retired key; a ciphertext copied between columns or
  tampered with; a resumed import commit after the hash column exists; a search whose text also
  matches encrypted notes; the legacy migration staging schema, which holds plaintext while a
  `ktl-migrate` load runs.
- **Out of scope.** CV and import binaries on disk, backup file encryption, word-level search
  indexes, user-account data and any frontend change.
- **Success criteria.** A `pg_dump` taken after rollout contains none of a seeded set of names,
  e-mails and phone numbers; every existing search, import and candidate test passes unchanged;
  the API refuses to start without keys; a query on an encrypted property fails the build; search
  meets the latency budget at the ceiling.
